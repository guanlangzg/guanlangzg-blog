## 系统性问题主题

- 发布与备份闭环在多处独立断链：候选摘要 candidateDigest 发布侧用 computeCandidateDigest、构建侧对冻结文件原始字节做 sha256，sealBuildOutput 的相等校验必然失败；withdraw 按 articlePath 记 /posts/<slug>/ 而快照校验只接受 /blog/<slug>/，撤回建站必然被拒；runner 阶段未 COPY public-site/app/manifest.ts 与 llms.txt/route.ts，容器内公开构建 ENOENT；GitHub 递归 tree 的目录项被当 blob 读取而 git/blobs 对 tree sha 返回 404，第二次起的完整备份即失败——四者互不依赖，修好一处并不能让「编辑→发布→备份→上线」跑通。
- 单个损坏文件或单个未捕获异常即可让任务 worker 永久停转，而健康与就绪检查只看数据根可写与 manifest 有效，Docker healthcheck 与部署回滚脚本都以 /api/health 为判据，完全观察不到 worker、job 状态或失败队列——坏 job 文件、坏 workflow/backup-state.json、deferClaimedJob 把 attempt 归零导致无限 1 秒重试，属同一静默故障族。
- 安全身份与请求来源依赖客户端可伪造的请求头：限流身份取自 X-Forwarded-For 且从不校验 TCP 对端地址、来源 origin 取自 Host/X-Forwarded-Host、登录 POST 无 Origin/CSRF 也无 Content-Type 校验；而交付模板默认 TRUSTED_PROXY_IPS 为空又让登录恒返回 503，构成「要么锁死、要么可绕过」的矛盾。
- 输入校验倾向静默归一化或有损丢弃，与文档「拒绝而非丢弃」的约定相反：非法/缺失 status 被归一化成 published，未闭合 --- 的 frontmatter 把正文整段吞掉，媒体扩展名不与 mimeType 交叉校验、恢复时也不重新嗅探字节，多条恢复读取路径不校验载荷自带 manifest——其中 status 归一化直接导致未发布内容匿名公开并进入 RSS/sitemap。
- 门禁与测试大范围「假通过」：覆盖率阈值配了但从没有任何脚本或工作流以 --coverage 运行，knip 配置缺 exports/types 使 deadcode 永不失败，CI 无 pull_request 触发，限流按 IP 隔离与 CSRF 正向路径用恒过条件断言，5 个公开动态路由的 force-dynamic 回归只有 1 处有守卫，另有一个间歇失败的用例。
- 凭据与秘密处理不一致：R2 的 secretAccessKey 以明文写入内容数据根 BLOG_DATA_ROOT/settings/cloudflare-r2.json（仅 chmod 0600，未加密、未与 GitHub 私钥一样放进 BLOG_SECRET_ROOT），secrets/ 目录既未被 .gitignore 也未被 .dockerignore 覆盖，而两套 compose 都把 ./secrets 挂在仓库工作树内。
- 前端状态与副作用管理脆弱：hydration 失配（useTheme 在 useState 初始化器直接读 localStorage）、列表用数组下标作 key 导致删除后编辑态串到别的条目、多处 setTimeout 无卸载清理、Cmd/Ctrl+S 无重入守卫会重复建文、草稿防抖在客户端跳转时丢掉最后不到 900ms 的输入。
