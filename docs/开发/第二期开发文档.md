# 第二期开发文档：第一版闭环补完与优化

> 文档性质：实施规格与验收计划，**不是完成报告**。编写日期：2026-10-01。这里的“第二期”指针对已做第一版代码的第二轮开发；它不改变[第一版开发文档](./第一版开发文档.md)的 R01–R14 上线门槛，也不把原讨论中的图表、封面和编辑器增强提前列为已完成。已确认的产品决策以[讨论汇总](../../最终博客项目讨论汇总.md)为准；本文件专门补足[第一版实施状态](./第一版实施状态.md)与 2026-10-01 代码复核之间的缺口。

## 1. 目标、范围与现状基线

**目标：** 在不替换原管理界面、不覆盖源项目数据的前提下，使“本地保存 → 私有 GitHub 完整备份 → 冻结候选 → 封存静态站 → 管理员预览并确认 → Pages 精确部署核验 → 已上线指针 → 新机合并恢复”成为管理员从界面可以完成、进程重启后可以续办的真实链路。只有 R01–R14 全部具备可观察的验收结果，才讨论替换 Pages 临时页。

**沿用：** React 18、Next.js 15、TypeScript strict、npm、Vitest、现有 JSON/媒体数据格式、GitHub App 与两个目标仓库、独立 Next 静态构建、单实例持久化任务、R2 可选兼容。沿用原有会话/CSRF/Origin 校验和 `EditorShell` 视觉体系。公网后台暂按已确认的 HTTP 5678 方案，传输风险仍然存在，不能宣传为已加密。

**不纳入本轮上线阻塞范围：** 图表模板与示例、doocs/md 式编辑增强、可选文章封面体验、更丰富的差异比较、备用域名与 HTTPS。保留这些已确认的最终需求，在核心闭环验收之后安排；本轮不会用二期功能代替 R01–R14 的缺口。

2026-10-01 复核基线：`npm run lint`、`npm run typecheck` 通过；Vitest **101 文件、757 项**通过；`npm run test:release` **19/19**；`npm run build` 首次并行运行在页面数据收集阶段报 `/_document` 缺失，随后**单独重跑成功**，尚无稳定复现的构建故障。`npm run deadcode` 失败，除 `@lhci/cli` 外，报告恢复解析器 `unified`、`remark-parse` 未直接声明；`src/public-site/**` 中由隔离构建脚本间接使用的文件不应按 Knip 结果直接删除。本机没有 Docker CLI；真实 GitHub App、Pages、VPS 和中国内地网络未实测。这些数字仅表示这次复核，不替代实施时重跑。

## 2. 实施路线与分阶段门槛

**方案比较：**

| 方案 | 好处 | 代价与结论 |
| --- | --- | --- |
| A：在现有存储、任务、公开构建、发布服务上逐段接线并修正边界 | 每段可用现有用例回归；保留兼容数据与视觉；审查时能定位失败环节 | 要补数据投影与任务状态迁移。**采用。** |
| B：一次性重写后台工作流和公开站 | 可以重新统一模型 | 范围跨数据/认证/构建/UI，旧 R2 与恢复兼容风险高；不采用。 |

顺序是 **S0 匿名访问封堵 → S1 GitHub 引导及可靠备份 → S2 候选构建与受保护预览 → S3 Pages 发布和复跑 → S4 后台恢复/历史/状态体验 → S5 容器和真实环境验收**。每阶段合并前须有该阶段的 API/行为测试和人工可操作结果；上一阶段的阻断错误未解决时，不用下一阶段的按钮或模拟结果宣称已闭环。阶段实现允许在单独开发分支逐段审查；本文件不授权任何自动 commit、push 或真实部署。

底层不变式：

1. `Article.status` 只表示编辑分类；Pages 上线只从经核验的 `live.json` 推导。构建器只读本候选冻结快照，不读全量实时草稿。管理旧路由只在鉴权后用于后台操作，绝不成为读者站或匿名预览的后备路径。
2. 发布确认须在同一内容短锁中核对 live 基线、所选输入/媒体、封存产物、**同世代的全局备份水位**和本候选 proof。无关内容的新备份未追平时返回 503，预览保留；所选输入变化或另一版本已上线才 stale。
3. GitHub 网络、Next 构建、Pages 轮询不能占内容锁；任务先持久化，远端副作用重试前先核对；确定失败与结果未知分开。发布不强推、不删库、不写源码仓库。
4. 私钥/口令/会话仅在服务端，内容备份白名单排除它们；Pages 只提交封存 `site/`，私有仓库完整保留已登记媒体与可读文章历史。恢复只写新的当前草稿/合并结果，不触发上线。

## 3. S0：先封住 VPS 草稿与媒体的匿名入口

**主要文件：** `src/middleware.ts`、`src/app/media/[...path]/route.ts`、`src/app/api/search/route.ts`，必要时拆出一个集中定义的“VPS 允许路径/内容路径”判定函数；测试 `tests/app/editor-middleware.test.ts`、`tests/app/media-route.test.ts`、新建 `tests/app/preview-routing.test.ts`。避免分别在多个公开页里增加零散登录判断。

- [ ] 列举 `/`、`/blog`、`/posts/*`、`/navigation`、`/search`、feed、sitemap、robots、OG、`/api/search`、`/media/*`、`/_site/*` 与 `.txt`/RSC 的请求归属；只有登录/健康与不含内容的管理静态资源可匿名获取。`/api/*` 不被公共页面 rewrite 意外改写，已有数据 API 保留其原本鉴权。
- [ ] 对匿名页面请求跳登录；JSON/图片/媒体返回 401/404。不能只凭 Cookie 存在放行：伪造、过期、无效会话都须拒绝；若 middleware 只负责初筛，最终内容 handler 仍必须逐请求验证真实会话。带 `next-router-prefetch`、`purpose: prefetch` 或 HEAD 也不能绕过。禁用旧 `/media` 的匿名长期缓存；管理员媒体预览须通过原会话验证并使用私有缓存。对公开品牌标识单独允许最小白名单。
- [ ] 无 `previewRelease` 的 VPS 公共内容请求不得回落到读取工作副本的 Next 页面。**登录的无 ID 页面**显示管理入口或明确提示；匿名跳登录。允许管理 UI 自身的 `/_next/*`，但 `/_site/<id>/*` 必须经过产物读取服务。主域 `guanlangzg.github.io` 的 Pages 静态站不受 VPS 中间件影响。
- [ ] 匿名集成夹具：本地保存一篇标为 `published`、从未上线且带秘密标记的文章、一个未发布导航条目和图片。逐一请求上述路由、搜索、图片、HEAD/prefetch，断言没有秘密字节；有登录的版本预览只返回冻结 B+C，不读工作副本 A。把之前匿名取图 200 的测试改成 401/404，并新增有会话成功用例。

**出口：** VPS 公网测试服务器上猜中 slug、媒体哈希、release ID 也取不到工作副本；没有对 `/api/editor-auth`、管理 UI 或 Pages 自身造成回归。在 S2 完整预览分流落地前，内容路由应保持拒绝，不暂时开放旧动态公开页。

## 4. S1：连接 GitHub App 并恢复主备份

**主要文件：** `src/app/setup/{page.tsx,SetupWizard.tsx}`、`src/app/api/setup/route.ts`、`src/app/api/editor/github/{route.ts,check/route.ts}`、`src/lib/github/{config,app,client,backup-service}.ts`、`src/lib/startup-tasks.ts`、`src/lib/jobs/{store,worker,watermark}.ts`、`src/app/api/editor/backups/route.ts`。旧 R2 配置和格式只做兼容验证。

- [ ] 首次部署先由隐藏 TTY `admin:init` 设强口令；登录后即使 GitHub 尚未连接，也可继续进入 `/setup`。把 `authInitialized`、GitHub 连接/权限检查、是否选择恢复、R2 可选、引导完成分为独立进度；不能因预设口令或 R2 设置就提前锁死向导。GitHub 失联时可以编辑草稿并显示待备份，但不允许发布；不用假定 R2 是主备份。
- [ ] 在原 `GET/PUT /api/editor/github` 上实现可重复的 `POST /api/editor/github/check`：扩展持久化 `JOB_TYPES`，加入受限的 `github-check` handler；仅已登录且通过 Origin/CSRF/body 上限的请求可排入检查 job，返回 202 + 可查询 job ID。worker 即使没有 `connected` 客户端也要启动；检查 handler 从 `pending` 配置与受保护私钥构造**仅用于验证**的 token 客户端，不能调用要求先 `connected` 的现有备份客户端，也不能让待检配置获得正常备份/发布权限。按约 15 秒的单次上游超时验证 App 身份、installation、Pages 与私有备份仓库身份/可见性/权限、Pages Source；只有实际核实后才写 `connected`。修改配置时重新置 `pending`；用配置 revision 防止旧检查结果把新配置误置已连接。缺私钥、权限、仓库非私有和网络错误分别展示，密钥不回显或记录值。
- [ ] 页面说明注册 App、仅安装 Pages 与备份两个仓库、源码仓库无写权限；显示已验证的仓库 ID 和权限。GET 返回安全 DTO；私钥输入使用完清空。R2 跳过时不再给出“无远端备份”的误导提示：若 GitHub 已连接则可跳过 R2，若尚未就绪则允许保存设置和草稿、显示未备份且阻断发布。
- [ ] 修复保存后完整备份：job 冻结正确世代、实际读取版本与 contentSequence，或持久化不可变输入；不要读到较新内容却标记旧序号为已备份。候选备份 proof 和全局完整水位分别推进；旧世代永不清当前 dirty。备份 job 达重试上限后给出可见失败与安全的手动重试，worker 空闲/周期检查 dirty 水位可补排，不依赖重启一次才恢复。
- [ ] 每日北京时间 03:00 核验私有仓库完整快照，停机错过在启动后补一次；记录上次成功核验时刻，不把“零变化”误报成未备份。30 秒静默合并、持续编辑 5 分钟上限及手动/请求发布即时排队按原 §6.4 验证；保存正文和上传未引用媒体均须在锁内登记备份待办。失联不阻塞本地编辑。
- [ ] `GET /api/editor/backups` 展示远端私有仓库可用 commit/时间/摘要的分页结果，用于新机恢复；本地 proof 只能作明确标识的缓存，失联必须显示“远端不可查询”，不能返回空列表冒充没有备份。所有响应仅含受限字段、`private, no-store`，保留原接口的 1–100 limit 约束。已创建但尚未执行的 `building` 候选若被备份逻辑扫描到，不得自动把已完成的全局备份误判为“候选已备份”；每个候选须有与其 digest 对应的 proof 才可进入构建和确认。

**测试与出口：** fake GitHub 严格检查仓库/私有性/权限/401/403/429、私钥脱敏、旧配置完成的竞态；真实进程杀死并重启后 pending/failed 任务仍可查询，双 worker 不重复提交；A 候选 proof 成功但 B 新保存未备份时不能确认，B 追平后原候选仍有效。无 App 的初次启动不应因 worker 初始化失败而永远停止处理 `github-check`。真实 App 的安装与 token 测试留到 S5，不以 fake 代替。

## 5. S2：从真实候选到封存字节与固定版本预览

**主要文件：** `src/lib/publishing/{service,snapshot,types}.ts`、`src/lib/editor-runtime/adapters.ts`、`src/lib/public-build/runner.ts`、`src/public-site/{types,views/**}`、`scripts/public-site/build.mjs`、`src/lib/jobs/{store,worker}.ts`、`src/app/api/editor/releases/**`、`src/app/api/editor/preview-files/**`、`src/middleware.ts`。新增一个专职转换模块，例如 `src/lib/public-build/from-release.ts`；只在这里投影业务候选为 `PublicSiteSnapshot`。

- [ ] 创建候选时，在内容锁内真正比较 `expectedRevision` 与作用范围对应资源的当前 revision；撤回以当前 live ID 为预期，首次 bootstrap 显式选择文章并校验组合 revision。移除 `readSelectedInputs` 中导致 bootstrap 所选文章恒为空的过滤条件。`selectedRevision` 的 generation 使用**恢复世代** `watermark.generation`，且类型与纯函数契约一致，不能用每次保存递增的 `contentSequence`。
- [ ] 候选事务固定 `SiteSnapshot`、candidateDigest、所选输入/媒体 identity；真实转换器只从此快照生成公开文章、完整导航/设置、已确认静态资产和受管媒体映射。无关草稿/未引用媒体不进入构建。公开站所需 UI 字段完整映射而非仅 `site.title/description`；页面、搜索、feed、sitemap、OG 用同一数据投影。空的可选文章摘要/日期保留为空并由页面/元信息显式处理，不能编造日期；真正必需的字段按文章 ID/字段名报告构建错误。
- [ ] 创建候选时给它排一个唯一的 `build` job，先在受控 build 根准备 `PublicSiteSnapshot` 输入 JSON 和**候选引用闭包**的媒体文件。现有 `build.mjs` 从输入 JSON 的同级 `media/` 读图片、且只复制声明了 `managedImage` 的资源；生产接线必须显式扩展受管媒体文件清单与构建脚本，使正文图片和既有 live 图片都能按原 SHA-256 字节导出，不能靠增加可选封面字段冒充正文媒体交付。worker 在候选备份 proof 已验证后，通过受控子进程调用现有 `scripts/public-site/build.mjs --snapshot <冻结输入> --out <全新的临时导出目录>`；输入/输出由服务端生成，不接受客户端绝对路径。脚本产物在 `<临时导出目录>/<releaseId>/`，而 `writeRelease` 已创建 `workflow/releases/<releaseId>/`；必须先核验产物，再把 `app/out` 与 `artifacts.json` 作为同一次可恢复的封存过程落到**现有 release 目录**，最后才标记 `preview_ready`，不能把 `--out` 直接指向已存在目录或覆盖 `release.json`/`snapshot.json`。崩溃留下不完整产物时拒绝预览并由同一 build job 对账/清理自有 staging 后重试。构建并发 1、超时、输出截断和环境白名单，不继承 App 私钥或 token；构建工作根为 `BLOG_BUILD_ROOT`。封存前后核验 release ID/candidateDigest、文件清单与真实字节；重复 job 不覆盖已生效产物。
- [ ] 构建完成后调用 `markPreviewReady`；它应保留备份 worker 已写入的有效 proof，不能被构建结果的 `null` 覆盖。构建失败写确定状态/脱敏原因，网络或排队未完成保持可查询进度；启动时恢复构建任务而不擅自替换已经确认的产物。
- [ ] VPS 页面带 `?previewRelease=<id>` 时按路径映射到同一个 `preview-files` handler，入口 `/`、普通文档导航、搜索索引、feed/图片、`.txt`/RSC/HEAD 均从固定产物取。当前该动态路由只有 GET，原 matcher 又排除部分 prefetch：路由映射与 handler 须一并覆盖 HEAD 与 RSC/预取请求，并以请求 URL/路径携带的 ID 比对会话活动 ID，不能用共享 Cookie 猜版本。`/_site/<id>/*` 按路径中的 ID 验证会话和 active ID；若请求另有查询 ID，也必须一致。内部 rewrite 可以补入该路径 ID 供 handler 检查，但不能从当前活动 Cookie 猜一个 ID。移除中间件的 prefetch 排除规则；静态预览只用封存的逐页脚本哈希 CSP，不注入管理页的随机 nonce，不改 HTML 字节。再次激活 B 后，A 标签页后续资源请求返回 409。
- [ ] 将正文媒体路径处理限制在 Markdown 图片/链接及经过校验的目标字段，不能全局 `replaceAll` 改写代码围栏和普通示例文本；编码与非编码路径、查询串有明确用例。发布前完整读取受管媒体真实字节并比对哈希。统一 release ID 的生成、路径校验与预览规则；资源越界和恶意路径返回 404。

**测试与出口：** 用真实本地 `POST /api/editor/releases`（不是手写 `PublicSiteSnapshot` 夹具）开始，等待 build job 达 `preview_ready`，核对 A 草稿不能出现在 HTML/索引/feed/media，B live 与本次 C 均存在。创建后无关 B 保存使备份门槛暂时 503，水位追平后**同一** artifactDigest 可确认；选中 A 改动则 409 stale。匿名、伪造 prefetch、两标签切换、普通导航和页面脚本在生产模式浏览器均验收。

## 6. S3：Pages 提交、核验、复跑与指针一致性

**主要文件：** `src/lib/publishing/{pages,retry,service}.ts`、`src/lib/editor-runtime/{adapters,github-runtime,retry-runtime}.ts`、`src/lib/jobs/{worker,store}.ts`、`src/lib/startup-tasks.ts`、`src/app/api/editor/releases/[id]/**`；在独立的受管目录提供核实过版本的固定 Pages workflow 模板。真实远端动作须经正式部署授权。

- [ ] 为 `publish`、`reconcile` 注册实际 handler；任务只引用 release ID、封存摘要和固定提交身份，唯一状态源为 `workflow/jobs`，**不要并行维护会漂移的 `publish-tasks` 副本**。读取现有副本前先定义兼容/迁移规则：保留旧记录供审计，从 job 真状态与远端事实判定可续办任务；不将历史失败任务标成功。无法初始化 GitHub 时 worker 保持本地可查/可恢复，发布任务显示配置阻断而非无 handler 重试至耗尽。
- [ ] worker 读取封存的 `app/out`，调用已有 `createPagesPublisher` 的生产适配器，只替换 Pages 仓库的 `site/`；核对父提交、固定工作流摘要、受管目录约定并 `force:false`。push 返回丢失时先通过提交/标识对账，不能再次盲推；远端网络操作不占内容锁。现有 `writeRelease` 先写 snapshot 后写 release、`live.json` 又单独落盘；在宣称“原子上线”前必须明确可恢复协议：逐状态持久化，发布指针提交失败时重启根据已核实的远端身份和保护记录安全续写或回滚，不允许 release 显示 live 而指针仍指旧版本。
- [ ] 状态依次持久化 publicCommitSha、指定 workflow run ID 与 **run_attempt**；同一个 attempt 的 deploy job 与 `Deploy to GitHub Pages` step 成功且线上 `/_release.json` 与 release/candidate/artifact 都一致后，才按上述恢复协议推进 release 与 `live.json`，并单独排队备份公开指针。超时保留 `verifying`；确定失败保留旧 live 与封存文件。重启后 reconcile 从持久化 commit/run 恢复，不能重复写 site。
- [ ] 复跑只对确定 failure/cancelled 开放，并坚持同一 run、同一提交、同一产物与新的 attempt；服务端重新计算所选输入/基线和校验封存字节，不拿 release 自身 revision 与自身比较。**已确认后的无关新 dirty 不能阻断此次复跑**；新的发布确认仍遵守全局门槛。注入生产部署核验函数，复跑成功要走与正常发布相同的 live 指针及指针备份事务。重复请求复用同一个真实任务，响应丢失先核查 attempt 再决定是否重发 POST。
- [ ] 修正发布占位生命周期：失败/结果未知时 UI 明示状态和可重试条件；既有 release 不应永久占用发布槽位且禁止取消一个远端结果未明的动作后直接发新版本。核验新 live 后旧候选基线失效。日志/API DTO 只暴露脱敏原因。

**测试与出口：** 假 GitHub 测错 SHA、branch、workflow、run/attempt、skip、旧现场 marker、非快进、push 后崩溃、部署后 live 写前崩溃、rerun 响应丢失；验收连续发布两个候选时旧候选 409、发布失败时读者仍见旧 live、复跑成功后 release 与 `live.json` 指向同一 ID/commit/attempt。真实仓库只在 S5 经授权的隔离测试与最终切换时验证。
